VOLTFILL · Architecture

PDFのテキスト層から、フォーム項目に当てはまる原文の値を根拠（Evidence）付きで返すUIなしのエンジンです。原則は「誤って埋めるより空欄」。Jevは候補の選択と値の位置の指示だけに使い、文字列は生成させません。

処理の流れ

PDF + フォーム項目
  → 読む       vf-source  テキスト片・座標・AcroFormの値（回転・縦書き・文字化けを検出）
  → 構造化     vf-source  行・ラベルと値の候補・表
  → 当てる     vf-core    厳格な照合で確定。確定できなければ理由(hold)付きの候補
  → 補う(任意) vf-core    --remote: 候補をJevに選ばせる / --images: ページ画像で位置を指させる
  → 返す       vf-core    項目ごとの status・原文・正規化値・Evidence

構成

利用者 / Webアプリ（別プロジェクト・計画）
   │ PDF + フォーム
   ▼
 vf-cli     voltfill（唯一の実行ファイル）── serve ──▶ vf-server  POST /v1/fill · GET /health
   │                                                    │
   ▼                                                    ▼
 vf-core    照合・正規化・Evidence ── --remote ──▶ vf-client ──▶ Jev API（choice / noul / box）
   ├─ vf-source  PDF解析・幾何・レイアウト
   └─ vf-render  ページ画像（hayro / PDFium、任意機能）
crate役割
vf-sourcePDF解析・テキスト片・座標・レイアウト（行・ラベルと値・表）・AcroForm
vf-render任意のページ描画。PDFiumは利用者が指定したライブラリだけを使う
vf-clientJevのプロトコル・送信・上限・全試行の受信本文の記録
vf-coreフォームの契約・照合・正規化・結果とEvidence
vf-server / vf-cliHTTPルート／CLI（設定・ログ・serve）
vf-legacy旧方式のText/Vision/Hybrid抽出。削除予定

基盤crate（vf-source・vf-render・vf-client）は vf-core 以上に依存しません。

守る約束

  • 値はPDFの原文から取り、生成・OCRしない。推定した座標は推定と明示する。
  • Jevへの送信は明示的な --remote が必要。全試行の受信本文を保存し、本文・認証情報・ヘッダーはログに出さない。
  • 結果は評価専用。confidenceは校正済みの確率ではなく、模擬応答の結果を実精度として扱わない。
